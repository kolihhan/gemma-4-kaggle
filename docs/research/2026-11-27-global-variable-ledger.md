## Early-edit residual error check — 2026-11-27
Reused the same external 1350 compact episodes (150 tasks, nine each). The published [schema](https://github.com/Aeterna-Data-AI-ML-Research/Kaggle-Gemma-4-Developer-Agent-Competition/blob/main/evidence/SCHEMA.md) explicitly excludes raw reasoning, raw command text and actual final diff blobs, so the data cannot support a blinded semantic review of individual final patches. "Opened all" includes shell argument mentions, not necessarily successful reads. First-edit marker is from the published detector, not an independent reconstruction. 
- Of 1,000 all-open episodes: 390 working-tree passes, 274 wrong nonempty patches, 336 empty patches. Among the 664 nonempty, 327 had a recorded first edit <=240s of the 420s virtual clock (237 correct/90 wrong), 323 >240s (149 correct/174 wrong), 14 without an edit marker (4 correct/10 wrong).
- Among the 90 early all-open nonempty failures: 46 submitted, 34 time-budget endings, 10 tool-budget endings, 64 distinct task-scoped 12-character patch hashes, 28 unique tasks. 82/90 fall on 21 of the 82 tasks never solved across nine episodes; these 82 include 46 submitted, 29 time-budget and 7 tool-budget ends. Not proof that the agent had sufficient context or finished its intended patch. Some successful or wrong diffs may have been produced by opaque shell edits.
- Exact same phase1 configuration two-seed contrast: 49 discordant pairs out of 450. Only 15 pairs where both arms were all-open and nonempty; only ONE also meets the 240-second early-edit condition for both arms. Thus the large conditional pooled rate cannot identify the causal benefit of earlier editing.
- 103 repeated nonempty task+patch-prefix groups, none with differing WT verdict in these public observations. Patch hash is truncated and not independently reconstructed; this is consistency evidence within the external local grader, NOT evidence that official LB variance is absent or that deterministic selection is solved.
- External author's earlier [P709 research matrix](https://github.com/Aeterna-Data-AI-ML-Research/Kaggle-Gemma-4-Developer-Agent-Competition/blob/main/research/reports/p709_task_research_matrix.md): 38 rows in never-but-reachable/deep-multihunk tiers; 12 edited a reference file but all observed rollouts failed, 10 author-coded incomplete type/branch coverage in same function, 4 never localized reference file, 2 off-by-one/regex/format mismatch; remaining 10 other heterogeneous labels, including 2 unsound environment. Historical author classifications, not independent adjudication or the same cohort; cannot sum with the 1350 episode evidence.

Decision: retain both wrong repair logic and execution/time allocation as plausible; even earlier observed edits plus full access do not guarantee a correct patch. Do not increase/decrease global thinking budget or introduce a generic second agent based on this retrospective. Next useful discrimination requires issue-only requirement annotation, actual visible evidence and retained patch behavior. Compact public traces cannot provide those three inputs. Prior private replay is blocked by API rate limit, so no valid replay data yet. No new GPU, training, official submission, or new architecture promotion.

### Proposed diagnostic, not an approved solver
Use an independent reviewer blinded to reference, outcome and candidate patch to extract an issue's explicit input conditions, expected output/invariant and compatibility/exception boundaries. Freeze this rubric; compare actual pre-edit evidence/rationale and candidate patch to it, then separately score behavior with issue-grounded tests when executable. Include stable pass and mixed contrast tasks; report missing/ambiguous and disagreement. If model's intended behavior contradicts the issue, investigate specification representation; if intention is correct but implementation violates it, investigate generation/verification; if intention cannot be recovered, remain UNKNOWN. A retrospective rubric does not prove an intervention helps. Before any new 31B run, compare independent fresh paired tasks with the same model, total budget and primary resolved metric, change one mechanism, require positive rescues/regressions and cost gate. No gold paths, patches, or hidden test knowledge as solver input. Do not call this a novel architecture: related requirements/witness approaches have already been attempted.
