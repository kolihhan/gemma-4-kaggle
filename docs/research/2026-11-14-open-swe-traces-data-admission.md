# Gemma 31B — external successful SWE trajectory admission gate (2026-11-14)

## Reason and exact benchmark target

The original Gemma 4 **31B / five-minute / 60-tool** coding agent is officially scored **0.180**, Kaggle entry `58183466`. Adding generic prompts, optional structured Skills and another model swap has not improved independent grader resolutions. The original E4B verifier-LoRA training-side harvest contains **0/18 approved positive action demonstrations**: directly copying failed traces would teach failure behaviors. This opens a *data-quality research hypothesis* but does not authorize training without actual clean positives and source-disjoint confirmation.

## NEW external dataset source, independently inspected

- NVIDIA public [Open-SWE-Traces v2.0](https://huggingface.co/datasets/nvidia/Open-SWE-Traces) is distributed under CC-BY-4.0, with underlying permissively licensed task repositories, `resolved` outcomes, model patch and tool-message records. [EMNLP 2026 research publication](https://aclanthology.org/2026.findings-emnlp.131/) describes the original dataset's grader-validated agent trajectories, **not** this specific model's eventual competition performance. The online v2.0 is materially larger than the version analyzed in the original paper.
- [Competition rules](https://www.kaggle.com/competitions/gemma-4-developer-agent/rules) allow generally accessible external data; public availability and licensing are **necessary, not yet a completed derivative training-rights audit**. The final submission still must use a supported Gemma 4 base and a legal ADK declarative bundle with optional LoRA adapters.
- Exact read-only source scripts: `scripts/audit_open_swe_traces_metadata.py` and `tests/test_audit_open_swe_traces_metadata.py`. The first iteration misread agent-named split `openhands`, etc., as missing `train`; source inspection corrected the selector to v2.0's agent-named splits. Large versioned dataset source catalog has **15 splits total** and **484 Parquet shards**, not an unavailable dataset.
- [Final verified live CPU source probe #43592847147](https://github.com/kolihhan/gemma-4-kaggle/actions/runs/43592847147) succeeded, checking four v2.0 splits: `claudecode`, `opencode`, `openhands`, `sweagent`; **6 first rows each = 24 non-random source rows**. Only aggregate schema/status counts entered public GitHub logs; no issue text, raw trace, reference patch, or agent command was saved/exported.
- Conservative syntax/quality check requires `resolved=1` (integer, not unknown), Python source, explicitly permissive repo license, repo not in the public competition dev set (`fastapi/fastapi`, `textualize/rich`, `psf/requests`, `encode/httpx`), a nonempty model-produced unified git diff and a trace containing both assistant and tool feedback. **16/24** rows pass this *preliminary gate*; **16 unique issue IDs and 16 unique repos** in this tiny sample. Each split has 4 passes and 2 not-resolved. This is **NOT** a random sample, full-corpus pass-rate estimate, trusted reward audit, or actual SFT training set.
- Crucial transfer test: among all 16 preliminary candidates, source tool catalogs are present in all 16, but **zero have any exact name overlap with the 9 official ADK native tools**. In this sample: `passing_with_any_exact_adk_tool_schema=0` for all four frameworks. Therefore copying vendor-native tool-call messages directly into Gemma 4 tool-calling supervision is **unsupported**; raw imitation is not equivalent to a correct ADK action sequence.
- No GPU, external training material copied to public repo, adapter trained, Kaggle private benchmark scored, or official submission created in these external-data investigations.

## Scientific decision

1. **Source viable as a clean-positive research lead** (there are 16 labeled successful, nonempty, tool-observed candidate trajectories across 16 unique public-project issues), unlike the old zero-approved raw traces. The labels refer to the dataset producer's original task tests, not the Kaggle 31B hidden harness.
2. **Source NOT directly trainable for Gemma 4 tool-call imitation.** Tool names/schema differ from permitted runtime, and the source contains model/provider-specific intermediate thoughts and feedback. No assumption that translating tool names alone preserves argument or command semantics; require a small exact action-schema adapter with tests, and drop any unverifiable tools/arguments.
3. **Before any SFT/QLoRA:** freeze a source revision and a disjoint held-out cohort; scan a larger deterministic, non-overlapping sample across versions/issues; isolate only successful provenance-clean rollouts; verify patch validity and source context; quantify exact ADK action conversion success against actual tool schemas; estimate 31B QAT adapter training feasibility with available GPU/hardware. Clear license/source attribution, especially original issue repositories and model output terms.
4. **Promotion criterion:** one final independently graded, disjoint Gemma 31B matched pilot must increase **resolved tasks**, not just training loss, tool action count, safe metadata count, or a successful CPU dataset scan. The official target remains **strictly above 0.180**.
5. **Stop/pivot trigger:** if no faithful conversion to runnable native ADK actions and no strong alternative evidence-to-patch supervision, reject *raw trajectory distillation*, rather than spend GPU on mislabeled “positives.” This does not permanently ban SFT/QLoRA, but rules out the naive current data path.

This report deliberately distinguishes 16 syntactically gated `resolved=1` source rollouts from **zero approved competition-ready ADK tool-call SFT examples**.


## Live observed external tool dialects (follow-up source probe)

[Authenticated GitHub CPU Action #43593187704](https://github.com/kolihhan/gemma-4-kaggle/actions/runs/43593187704) completed successfully on the same 24 real v2.0 dataset-viewer rows with a new **allowlisted schema-only** extraction: public tool names and argument *key names*; no commands, values, agent messages or code fragments exported. The 16 candidate row / 16 distinct issue / **0 exact native ADK tool-name** counts reproduce.

| External scaffold | Public tool names observed | Transfer to official ADK tool contract |
|---|---|---|
| Claude Code | `Bash`, `Read`, `Edit` | **Undetermined**; catalog parser did not expose argument-key metadata for these declarations. Do not assume they are mappable. |
| OpenCode | `bash(command,timeout,workdir)`, `edit(filePath,oldString,newString,replaceAll)`, `read(filePath,offset,limit)`, `write(content,filePath)`, also `glob`, `grep`, `skill`, `task`, `todowrite`, `webfetch` | **Potentially partial**: shell/file actions have analogous native tools, but path/offset/multiple-edit/timeout semantics and tool-result shapes differ; `task`, `webfetch` etc. have no direct registered ADK counterpart. |
| OpenHands | `execute_bash(command,is_input,timeout)`, `str_replace_editor(command,path,old_str,new_str,...)`, `finish(message)`, `think(thought)` | **Conditional**: a branch of editor commands might map to native `edit_file`; input mode and editor commands cannot blindly map. |
| SWE-agent | `bash(command)`, `str_replace_editor(command,path,old_str,new_str,...)`, `submit()` | **Most plausible restricted bridge** at the *declared-schema* level; must still check actual source call arguments, path safety, feedback serialization and `submit_patch` lifecycle. |

Official native [`HARNESS_README.md`](../../HARNESS_README.md) exposes `run_command(command)`, `read_file(filepath,start_line,end_line)`, `edit_file(filepath,old_string,new_string,allow_multiple)`, `write_file(filepath,content)`, and `submit_patch()` with **non-identical** semantics to the external scaffolds. This schema comparison is evidence of *possible* mapping tasks, **not an implemented mapping, positive imitation dataset, or policy/solver improvement**. A safe adapter must explicitly reject opaque/non-equivalent actions; no instruction rewrite should claim a foreign agent's tool call is native.
