## Critical corrected facts

1. **Official scorer metric bug:** [organizer Ryan Holbrook on 2026-11-18](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/760126) says score calculation let some submissions earn improperly high scores; affected scores were recalculated. **Do not promote the formerly seen 0.29 peak as a real target or assume current LB unchanged.** This is a STAFF declaration, not a participant theory.
2. [Official model availability](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/748287) now supports 31B, 12B, E4B, E2B. No within-submission mixed-size multiagent. However [31B vs 12B vs E4B, local 31 tasks](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/750974) reports 31B solved 9 and 11/31, 12B 4/31, E4B 0/31; a smaller LM was not necessarily faster per *completed task*. Single local task mix/hardware differs from official scorer.
3. [Training loss fails to transfer](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/751596): three 31B LoRA variants lowered loss without improving paired 98-task solves (prompt-only reference 38; A1 31, A2 37, A3 31). [E4B paper notebook](https://www.kaggle.com/code/dheerajpiduru/gemma-4-e4b-what-moved-the-score-and-what-didn-t) shows teacher imitation loss .49→.35 yet 3 solves/87 test runs vs 6 plain E4B; edited often but submitted too late. Neither proves all targeted training fails.
4. [Local 114-case 1,800+ trials](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/760014) author reports E4B organizer zero-think 16/114 vs 4096-think 10/114, best custom 15/114; training, extra thinking, serial roles often lost. **Selection confound:** a “successful runs finish before 12 calls” association does NOT establish that an imposed 12-call stop improves success. Dedicated paired interventions required.
5. [LoRA inference overhead](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/760309): author tested A100 22–25% throughput reduction and local 129 task base 57 vs mathematically zeroed adapter 50, same nominal policy. This is compelling mechanism evidence for serving path overhead or numerical/behavioral path effects; not a direct 4×L4 scorer result. [31B adapter OOM](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/749191) and [tool parser infinite loop](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/753973) show infrastructure can be an actual gating issue.
6. [Evaluator environment gold patch calibration](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/751487) improved reference gold patch pass from 52/129 notebook-style to 127/129 scorer-like sandbox **on their own reconstruction**; their author explicitly did not claim a perfect scorer match. Our 15/15 gold-valid previously selected cases are real but only support 15 cases, not arbitrary 129.
7. [Teacher harness comparison](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/747168): Gemma31B ~54/124 vs stronger teacher 58–59/124 under same reported tools/budget, with seed discordance. Suggests harness/task interface significant but teacher model comparisons not official Kaggle scores.
8. [Public code port](https://www.kaggle.com/code/victorzhong0110/gemma4-pack-lb-0-22-40-tool-calls) has 40 calls, pinned task statement after compaction, instant submit; **port says it does not independently claim a scored result**. The upstream 0.22 is a notebook author claim; do not conflate a forked title with authenticated account score.
9. [Paper on score power](https://www.kaggle.com/code/mobassir/why-your-leaderboard-can-t-see-a-3-point-gain) claims identical-file re-executions vary ~1.5 tasks on a public sample sometimes described as 58; the number of tasks and evaluation semantics are not independently confirmed on current scorer. A separate paper notebook says its own 692-run aggregates conflict by 17 successes and its assumed 58-task denominator fails to explain some displayed score decimals. Treat simulated power as caveated, not a ground-truth noise parameter.

## Our repository consequence

As of latest inspected `NOW.md`, authenticated best 31B **0.18**, official one-variable external 31B Coder-LoRA submission **#58558350 PENDING** as logged 2026-11-19. It is **not yet a success**. Its packaging was validated, but no evidence demonstrates actual vLLM LoRA activation, counterfactual task improvement, or stable 4×L4 runtime. Avoid another LoRA derivative until this run resolves and the one-variable result can be interpreted against serving-cost / statistical noise risks.

**Main mechanism to investigate first**: task success funnel on gold-valid tasks — (a) reaches relevant file, (b) attempts correct region edit, (c) produces valid diff, (d) checks semantic requirements/tests, (e) submits in time. Distinguish tool parser/serialization or stale environment defects from model choosing an ineffective next action. Predeclare stage-level rescues and regressions. Don't optimize BM25 hit@5 as if it equals final PASS: our own source-first BM25 .64 vs graph .30 hit@5 but E2E 7/12 vs 9/12 on a tiny dev panel. Preserve 31B scored control while testing bounded task/agent policy alternatives; small models and costly adapters are experimental hypotheses, not defaults.

## Strong competing explanations
- Harness/serving issue: zero adapter path can regress without learning.
- Task policy: call budget distribution / delayed patch may dominate.
- Semantic program repair: model reaches file but invents wrong patch.
- Scorer power: sparse and noisy Public outcome cannot resolve 1-task improvements.
Any one of these can be dominant for a given run; no paper source alone establishes relative contribution on our exact 0.18 bundle.

No GPU, new Kaggle submission, model training or private scoring executed in this audit.
